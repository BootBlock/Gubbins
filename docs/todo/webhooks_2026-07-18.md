# Webhooks — grounding research + phased implementation plan

> **Status:** 🟢 ACTIVE — plan landed and revised after review; no phase implemented yet. `W0` is next.

Driven by [issue #87](https://github.com/BootBlock/Gubbins/issues/87): *"add full and comprehensive
support for webhooks from directly within the Gubbins PWA itself"* — when something happens in
Gubbins (an item is created, an item moves to a new location, …), call out to a user-configured
URL carrying that event.

Each task has a stable ID (`W0`, `W1`, …) so a session can be kicked off with just "implement `W3`".

---

## 1. Verdict

**Build it — but split it along the line the browser draws, not the line the issue assumes.**

The issue's framing ("webhooks from directly within the PWA") implies the browser both *decides* and
*delivers*. The research in §2 shows a browser **cannot reliably deliver** a webhook to the endpoints
users actually own, for four independent reasons. Meanwhile the bridge already delivers webhooks
well, and has since EI-1 ([ecosystem-integrations_2026-07-03.md](ecosystem-integrations_2026-07-03.md) §A1).

So the plan splits responsibility:

| Concern | Where it lives | Why |
| --- | --- | --- |
| **Configuration** — which URL, which events, which filters, what payload | **The PWA** | It is a user-facing feature and belongs in the app's UI, synced like every other user record. This is the whole of what issue #87 is really asking for. |
| **Decision** — "this event matches this subscription" | **Shared pure module in `src/`** | One rule engine, unit-tested once, imported by both sides across the existing `@/` seam. |
| **Delivery** — the actual HTTP call, retries, signing | **The bridge (primary)**, PWA (narrow fallback) | The bridge has no CORS, no CSP allowlist, no mixed-content rule, and keeps running with the tab shut. |

The user never has to think about this split: they add a webhook in the app, and the app tells them
plainly where it will be delivered from and what that implies.

### 1.1 What already exists — and what it actually costs to reuse

> **This section was corrected after review.** The first draft claimed the app could import the
> bridge's event model directly and that the deliverer could be reused unforked. **Both were wrong.**
> The corrected costs are the single largest change between drafts.

- **The event model** — [`bridge/src/events/model.ts`](../../bridge/src/events/model.ts) maps every
  `HistoryAction` to a stable dotted type (`item.created`, `item.moved`, `stock.adjusted`,
  `item.low_stock`, …), derives status events, and carries a deterministic `id` for dedupe. It is
  pure and well-tested — but it **lives on the wrong side of a one-way boundary**.
  [`tsconfig.app.json`](../../tsconfig.app.json) has `"include": ["src"]`, and the root
  `tsconfig.json` is `files: []` + project references; the bridge is a separate `tsc -p` invocation.
  The `@/*` alias runs **bridge → app only**, deliberately — see the doc comment at the top of
  [`bridge/tsconfig.json`](../../bridge/tsconfig.json), and
  [`push-to-bridge.ts:15`](../../src/features/sync/push-to-bridge.ts#L15), which states outright that
  it imports *nothing* from `bridge/`. No file under `src/` imports from `bridge/` today.
  ⇒ **`W0` relocates the pure model into `src/`.** Not free: `model.ts` is consumed by
  `generation.ts`, `pipeline.ts`, `webhook.ts`, `sse.ts`, `lookup.ts` and their tests, and its
  `ItemSummaryDto` dependency on the bridge's frozen public DTO contract must be inverted.
- **The deliverer** — [`bridge/src/events/webhook.ts`](../../bridge/src/events/webhook.ts): HMAC-SHA256
  signing, `X-Gubbins-Delivery` id, per-target FIFO queue, exponential backoff, failure circuit,
  bounded queue. Excellent, and the retry/circuit machinery is reused as-is — but its `WebhookTarget`
  is `{ url, secret, events? }` with a **required** secret, and its `FetchLike` is
  `{ method, headers, body } → { ok, status }`. It has no concept of per-subscription HTTP method,
  extra headers, payload templates, filters, GET query-flattening, SSRF policy, or outcome capture.
  ⇒ **`W5` is a substantial extension of the target model and request builder**, not a drop-in.
- **The search hook the issue asks for** — *"a hook is called when (e.g.) a search is performed"* is
  **genuinely already shipped** as `lookup.resolved`
  ([`bridge/src/events/lookup.ts`](../../bridge/src/events/lookup.ts), task A2), behind its own
  deliberate opt-in because it publishes what someone searched for. `W7` only surfaces it in the UI.

## 2. Grounding research — why the browser cannot be the deliverer

This is the evidence for §1, recorded specifically rather than as a summary judgement, because it is
the part most likely to be re-litigated.

### 2.1 CSP pins the outbound origin list at build time

[`src/csp.ts:37`](../../src/csp.ts#L37) sets:

```
connect-src 'self' https://www.googleapis.com https://world.openfoodfacts.org
```

A user-supplied webhook URL is not on that list, so the fetch is blocked before it leaves the page.
The policy is enforced **twice** — as a service-worker response header ([`src/sw.ts`](../../src/sw.ts))
*and* as a build-time `<meta http-equiv>` injected from `vite.config.ts` — and a browser enforces the
**intersection** of all delivered policies. That kills the obvious workaround: the service worker
could compute a per-user `connect-src` from stored config, but the static `<meta>` would still veto
it. Supporting arbitrary user URLs from the browser therefore means broadening the *committed* policy
for every user, including those who never configure a webhook.

### 2.2 CORS blocks the request the design needs

A signed webhook is by definition a cross-origin `POST` with a custom header
(`X-Gubbins-Signature`) and `content-type: application/json`. Both make it **preflighted**, so the
receiver must answer an `OPTIONS` with permissive CORS headers. Most webhook receivers do not:
Slack's incoming webhooks and Home Assistant's `webhook` trigger send no CORS headers at all.

The escape hatch, `mode: 'no-cors'`, is worse than it looks — it forbids custom headers (**no
signature**), restricts `content-type` to `text/plain` / form encodings (**no JSON**), and returns an
opaque response (**no way to know if it worked**, so no meaningful retry and no delivery log). A
webhook that cannot be authenticated and cannot be confirmed is not the "full and comprehensive"
support the issue asks for.

### 2.3 Mixed content rules out the primary audience

Gubbins ships to an HTTPS origin. A browser on an HTTPS page cannot fetch `http://` — and the
receivers this feature is for (a Home Assistant instance, a Node-RED flow, a self-hosted automation
box on the LAN) are overwhelmingly plain `http`. Already hit and documented in
[`scale-reading.ts:10-11`](../../src/features/inventory/scale-reading.ts#L10-L11), where the reading
is fetched *via the bridge* precisely because the PWA cannot reach Home Assistant directly.

### 2.4 Nothing delivers with the tab closed

[`src/sw.ts`](../../src/sw.ts) registers no one-shot Background Sync listener, and its `periodicsync`
handler explicitly cannot do work itself — it only messages live windows. The database is held under
an exclusive Web Lock by a single tab ([`src/db/tab-lock.ts`](../../src/db/tab-lock.ts)), so a service
worker cannot read a queued delivery even if one existed. A webhook queued as the user closes the tab
is simply lost.

> **Pre-existing bug found during this research — file separately, out of scope for #87.**
> `pushSnapshotToBridge` ([`push-to-bridge.ts:71`](../../src/features/sync/push-to-bridge.ts#L71)) and
> `scale-reading.ts` both fetch a **user-supplied bridge URL absent from `connect-src`**, both sending
> an `authorization` header (so both are preflighted). In a production build these should already be
> CSP-blocked, and `pushSnapshotToBridge` catches the failure into a message that reads as "the bridge
> is offline". Direct corroboration that the PWA-direct outbound path is not currently viable.

### 2.5 What the browser *can* do

Direct delivery works for endpoints that are **HTTPS *and* CORS-permissive** — Discord webhooks are
the notable example, and many SaaS "catch hook" endpoints (Zapier, Make, IFTTT) qualify. A real but
narrow minority, so `W6` supports it explicitly and honestly rather than pretending it is the general
case. It still requires the CSP decision in §6.3, and remains **droppable**.

## 3. Architecture

```
                    ┌──────────────────────── the PWA ────────────────────────┐
                    │                                                          │
  item_history ───▶ │  event derivation ──▶ subscription matcher ──▶ delivery  │
  (existing ledger) │  (shared src/ module)   (shared, pure)          queue     │
                    │                              ▲                            │
                    │                   webhooks table (synced)                 │
                    └──────────────┬───────────────┬───────────────────────────┘
                                   │               │
              route='direct' only, │               │ rides the existing snapshot
              only on the pinned   │               │ push / sync to the bridge
              device               │               │
                                   ▼               ▼
                          the user's endpoint   ┌─── the bridge ───────────┐
                                                │ reads subscriptions from │
                                                │ the hydrated DB; delivers│
                                                │ route='bridge' ONLY      │
                                                └────────────┬─────────────┘
                                                             ▼
                                                    the user's endpoint
```

### 3.1 Who delivers — the disjointness rule

> **Added after review.** The first draft had app-side derivation *and* bridge-side delivery reading
> the same ledger with independent cursors, and resolved `auto` at *delivery* time by asking "is the
> bridge reachable?". That bakes in **duplicate delivery**: the app's "the bridge is reachable, I'll
> stand down" and the bridge's "I haven't hydrated that subscription yet" are guaranteed to disagree
> during exactly the window that matters. Multi-device made it worse — three synced devices meant
> three POSTs per event, with no coordination signal available.

**The fix is to make the two deliverers disjoint by construction, so no arbitration protocol is
needed at all:**

1. **`route` is resolved at *configuration* time, not delivery time.** The stored value is always
   concrete — `bridge` or `direct`, never `auto`. `auto` exists only as a UI affordance that picks
   one and explains the choice; it is never persisted.
2. **The bridge delivers `route='bridge'` and nothing else.** It ignores `direct` rows entirely.
3. **The app delivers `route='direct'` and nothing else.** It never attempts a `bridge` row.
4. **A `direct` subscription is pinned to one device** via a `direct_device_id` column. Only the
   device whose id matches delivers it; every other device shows it as "delivered from *<device>*"
   and stands down. This is what stops N synced devices firing N times.

The event `id` remains deterministic, so a receiver *can* dedupe — but the design must not rely on
that, and the wiki must not quietly push the problem onto the user.

### 3.2 The bridge reads subscriptions from the DB it already hydrates

The bridge **already hydrates the app's database**. So subscriptions in a synced table are readable
by the bridge with **no new config endpoint, no new token, no new auth surface** — merged with the
existing `webhooks.json` / env targets, which stay supported for operators who prefer file config.

Two honest caveats, both of which must reach the UI and the wiki rather than being buried:

- **Latency.** A new subscription becomes live when the next sync/push reaches the bridge, not
  instantly.
- **One new *read* endpoint is still required.** The bridge is strictly read-only over a snapshot
  that is **swapped wholesale on every hydration** ([`generation.ts`](../../bridge/src/events/generation.ts),
  [`pipeline.ts`](../../bridge/src/events/pipeline.ts)), so it **cannot write delivery outcomes back
  into the DB** — anything it wrote would be discarded on the next hydrate. The bridge therefore keeps
  its own delivery log and exposes `GET /api/v1/webhooks/deliveries` on the existing bearer auth,
  which the app polls **only while the Webhooks screen is open**. Without this, the delivery log and
  "send test event" — the feature's primary debugging affordances — would show nothing at all on the
  *recommended* route.

### 3.3 Event derivation in the app

The app has **no event bus today** — no emitter, no `BroadcastChannel`, nothing observing writes.
Building one would mean touching ~30 scattered `historyStatement(...)` call sites, which is exactly
the drift problem [`invalidate.ts:19-21`](../../src/features/inventory/invalidate.ts#L19-L21) already
documents having been bitten by.

**So the app does what the bridge does: derive events by diffing the ledger, not by intercepting
writes.** `diffNewEntries` / `buildEvents` already do exactly this and are relocated to `src/` by
`W0`.

**The ledger is therefore the contract**, with two limits that must be stated in the UI, not just
here:

- **No ledger row → no webhook.** `W2` audits which user-visible actions write no history row, so the
  blind spots are known rather than discovered by users.
- **The window is lossy.** `DEFAULT_EVENT_SCAN_LIMIT = 100` and `DEFAULT_FAN_OUT_CAP = 50`. A bulk
  import writes far more than 100 ledger rows in one go and will emit `events.truncated` instead of
  the user's events. For a feature promising "call my URL when an item is created", this is the more
  surprising limit of the two.

**Cursor persistence is a genuine fork, and `direct` is lossy either way:**

| | Behaviour | Consequence |
| --- | --- | --- |
| Cursor **persisted** | `previous !== null` on load, so the cold-start baseline never fires | Reopening after a week replays the window as a burst |
| Cursor **not persisted** | Baseline fires, emitting nothing | Every event written while the tab was closed is **silently dropped forever** |

**Decision: persist the cursor, bounded.** On load, if the gap exceeds the scan window, emit nothing
for the overflow and record a *"some events were missed while the app was closed"* marker that the
Webhooks screen surfaces. This is the honest option — and it is precisely why **`route='bridge'` is
the recommended route and `direct` is documented as best-effort**: the bridge runs continuously and
does not have this problem.

**Where the pump runs:** a new always-mounted, renders-nothing component, mounted like
`ReminderNotifications` ([`src/App.tsx:65`](../../src/App.tsx#L65)) — but note that precedent covers
**mounting only**. `ReminderNotifications` is query-driven, not a polling loop; a polling ledger-differ
is a **new pattern** in this codebase and should be reviewed as one. It is gated on the `webhooks`
feature being on *and* at least one enabled `direct` subscription pinned to this device existing, so
users who never touch webhooks pay nothing.

## 4. Data model

Two new tables, both folded into the **squashed v1 baseline** per the pre-release policy in
[`src/db/migrations/index.ts`](../../src/db/migrations/index.ts) — *not* a v2 migration.

### 4.1 `webhooks` — the subscriptions (synced)

Shaped like the `wishlist` / `tare_presets` precedent: an independent LWW leaf, no FKs, `STRICT`,
UUID TEXT PK, UNIX-ms timestamps, and the standard `updatedAtTrigger` helper (never an inlined
trigger — the `MAX(now, OLD.updated_at + 1)` and `WHEN NEW.updated_at = OLD.updated_at` invariants are
load-bearing for sync).

| Column | Notes |
| --- | --- |
| `id` | UUID |
| `name` | user label, e.g. "Discord #inventory" |
| `url` | `http(s)` absolute |
| `method` | `POST` \| `GET` \| `PUT` \| `PATCH` — the issue explicitly asks for more than POST |
| `enabled` | integer bool |
| `secret` | HMAC signing secret; nullable (§6.1) |
| `secret_ref` | name of a bridge-side secret, for users who keep it out of sync (§6.1); nullable |
| `event_types` | JSON array of dotted types, or `["*"]` |
| `filter` | JSON filter expression (§5.2), nullable |
| `template` | payload template (§5.3), nullable = default envelope |
| `headers` | JSON object of extra static headers, nullable |
| `route` | `bridge` \| `direct` — **always concrete, never `auto`** (§3.1) |
| `direct_device_id` | the one device that delivers a `direct` row (§3.1); null for `bridge` |
| `created_at` / `updated_at` | standard |

### 4.2 `webhook_queue` — pending work **and** delivery log (local, **not** synced)

> **Corrected after review.** The first draft's diagram showed an "outbox" that §4 never defined,
> while separately defining a `webhook_deliveries` **log** described as prunable telemetry — and you
> cannot prune a pending queue as telemetry. They are now one table with an explicit lifecycle.

One local table with a `status` column (`pending` → `delivering` → `succeeded` / `failed` /
`abandoned`). Records `subscription_id`, `event_id`, `event_type`, `payload`, `status`,
`attempted_at`, `status_code`, `error`, `attempts`, `route`.

- **Per-device, deliberately absent from `SYNC_TABLES`** — it is device telemetry, and syncing it
  would be pure churn *and* would leak delivery state between devices that must stay independent.
- **Only terminal rows are pruned**, on a rolling per-subscription cap. Pending rows are never
  pruned by the retention sweep.
- **Never log the secret, the signature, or full request headers.** Follow the existing deliverer's
  `redactUrl` (origin + path, query dropped).

## 5. Feature design

### 5.1 Event catalogue

The subscribable list is a **hand-maintained catalogue assembled from four sources**, with a drift
test asserting it stays a superset of what the engine emits:

> **Corrected after review.** The first draft claimed the catalogue could be *generated* from
> `ACTION_EVENT_TYPE` such that it "cannot drift". It cannot: `eventTypeForAction` falls back to
> `'item.changed'` for unknown actions (an **open set**, so the reverse direction isn't derivable),
> `events.truncated` is emitted and absent from the map, `item.low_stock` / `item.out_of_stock` are
> derived in `statusEvent`, and `lookup.resolved` lives in `lookup.ts`.

Presented in the UI as a grouped, human-labelled picker, never a raw string field. Includes
`lookup.resolved`, which the UI must mark clearly as *"publishes what was searched for"* and leave off
by default, mirroring the bridge's deliberate separate opt-in.

### 5.2 Filters

Beyond event type, a subscription can narrow by a small, **declarative, JSON-serialisable** filter —
location subtree, category, tag, item, or a quantity threshold. It must be a data structure evaluated
by a pure matcher, **never** a user-supplied expression string that gets `eval`'d or interpreted.
Follow the existing search AST discipline (`parseTextQuery` → AST → evaluate; memory note
`phase-47-scope-decisions`) rather than inventing a second query language.

### 5.3 Payload templates

Default is the existing `BridgeEvent` envelope — unchanged, so anything already consuming bridge
webhooks keeps working. Optionally the user picks a **preset** (Discord, Slack, Home Assistant,
generic) or supplies a template with `{{event.type}}`-style placeholders resolved by a pure,
**allow-listed** interpolator: an explicit list of permitted paths, no arbitrary property traversal
and no code, so a template can never surface something the event did not already contain.

For `GET`, the payload flattens into query parameters instead of a body (the issue explicitly asks
for `GET`); the UI must note that a `GET` cannot carry an HMAC body signature.

### 5.4 Route selection in the UI

Per §3.1 the stored `route` is always concrete. The **route badge is a first-class part of the UI**,
not a buried setting — a user must see at a glance why a webhook is or is not firing, and on which
device. This is the single most likely source of "it doesn't work" confusion and the design should
absorb that cost up front:

- choosing `direct` warns that `http://` and non-CORS endpoints will fail, that delivery stops with
  the tab, and that it is pinned to *this* device;
- choosing `bridge` states the hydration latency (§3.2);
- a `direct` row viewed on a non-pinned device shows "delivers from *<device name>*", with a
  re-pin action.

### 5.5 Test-fire

Every subscription gets **"Send test event"**, producing a synthetic event through the real matcher,
template and delivery path, writing a real queue row. For `route='bridge'` the result arrives via the
`GET /api/v1/webhooks/deliveries` poll (§3.2) — which is why that endpoint is not optional.

## 6. Security

### 6.1 The secret — the one genuinely new decision, and it has no clean answer

> **Corrected after review.** The first draft proposed "store it in the row, let it sync, but redact
> it from backups via `SYNC_EXCLUDED_COLUMNS`". That is **self-defeating**:
> `SYNC_EXCLUDED_COLUMNS` ([`tombstone.ts:179`](../../src/db/repositories/tombstone.ts#L179)) is
> applied inside the *shared* snapshot builder used by sync, backup **and** the bridge push, so
> excluding `secret` there strips it from the very payload the bridge hydrates — **bridge signing
> dies**. A backup-only redaction would be `filterSnapshot` in
> [`backup-format.ts`](../../src/features/backup/backup-format.ts) instead, but even that is defeated
> by `rawSqlite` (a byte copy of the whole DB) in `build-backup.ts`. And the draft worried about the
> backup while ignoring the leakier artefact: the **sync** file, which by design sits on a NAS or in
> the user's Google Drive.

The constraint is unavoidable: **for the bridge to sign, the secret must reach the bridge, and the
only channel to the bridge is the synced snapshot.** So the options are:

1. **Secret in the row, synced (default).** Works everywhere, including `direct`. The secret lives in
   the sync artefact in plaintext. Mitigate by generating it (never user-invented), showing it **once**
   with a copy button, offering regenerate-only afterwards, and **documenting plainly in the wiki**
   that a webhook secret travels with synced data.
2. **`secret_ref` — bridge-side secret (opt-in).** The row stores only a *name*; the value lives in
   the bridge's git-ignored `webhooks.json` / env and never syncs. Strictly better for users who
   accept the extra setup step, but **cannot support `direct`** (the browser has no access to it).

**Proposal: ship both** — option 1 as the default because it works with zero setup, option 2 offered
for `route='bridge'` users who want the secret out of their sync artefact. **This needs a conscious
decision in `W1`**, flagged here so it is reviewed rather than discovered.

### 6.2 SSRF and the local network

A user-configured URL is a request-forgery surface — most sharply on the **bridge**, which sits on the
LAN and can reach things the browser cannot. The bridge must refuse to deliver to
loopback/link-local/metadata addresses unless the operator explicitly opts in via an env flag, in
keeping with the bridge's existing off-by-default posture for anything with reach.

### 6.3 CSP

Direct delivery (`W6`) requires broadening `connect-src`. **The narrowest change that works is the one
to make**, and it needs an explicit decision recorded in `W6` before any code lands:

- broaden to `https:` only (never `http:` — mixed content blocks it anyway, so allowing it buys
  nothing but surface area);
- keep `'self'` and the two existing origins explicit;
- state the trade-off in the `csp.ts` doc comment, which is that file's established convention.

If the trade is judged not worth it, **`W6` is droppable** — the feature still works via the bridge,
which is the recommended route regardless. `W6` is sequenced last so this stays a live option.

### 6.4 Everything else

No secret, signature, or token in any log, error message, or queue row. `redactUrl` for diagnostics.
User-supplied extra headers are validated against a deny-list so a template cannot forge
`authorization` onto an unrelated host without the user's intent being explicit.

## 8. Touch-point checklist

Every one of these is required, and several **fail the build** if missed rather than merely being
forgotten.

**DB** — `migrations/v1-initial.ts` (2 × `CREATE TABLE` + `updatedAtTrigger` + indexes) ·
`__fixtures__/schema-baseline.snapshot.json` (**deliberate regeneration** — `v1-initial.test.ts`
asserts byte-for-byte, so this fails by design until updated) · `repositories/WebhookRepository.ts` ·
`repositories/index.ts` (export **and** `getWebhookRepository()` accessor — two separate blocks) ·
`repositories/types.ts` + mapper · `tombstone.ts` `SYNC_TABLES` (`webhooks` only — **not**
`webhook_queue`).

**Modules** — `feature-registry.ts` (`FeatureId` **and** `FEATURE_DEFS`; typed `Record`, so one
without the other is a compile error) · `nav-destinations.ts` (`AppRoutePath` **and**
`NAV_DESTINATIONS`; a registry-integrity test asserts the route↔feature pairing both ways) ·
`presets.ts` · `en.json` **and** `de.json` (the `messageKey` value must be **byte-identical** to the
`NavDestination.label` — a drift test pins it).

**Routes** — `src/routes/webhooks.tsx` wrapped in `ModuleGuard` · regenerate `routeTree.gen.ts`

**Bridge** — target sourcing from the hydrated DB · `route` honouring · SSRF guard · the new read

**Docs** — `docs/wiki/` page + sidebar + page map in `wiki_2026-07-11.md` · this doc's status banner

## 9. Testing

- **Pure modules** (`W2`, `W3`) — exhaustive unit tests; this is where the real logic lives and it is
  all I/O-free by construction.
- **`W0`** — the existing bridge event tests must pass unchanged; that is the refactor's proof.
- **Repository** (`W1`) — against the `node:sqlite` in-memory driver, as every other repository does.
- **Delivery** (`W5`, `W6`) — the existing `webhook.test.ts` injects `fetchImpl`, `sleep` and `now`;
  follow it exactly. No real network in tests.
- **Duplicate-delivery guard** — an explicit test that a `route='bridge'` row is never delivered by
  the app pump, and a `route='direct'` row never by the bridge (§3.1). This is the invariant the whole
  design rests on; it deserves a test that names it.
- **`npm run smoke:bridge`** — mandatory for `W0` and any change reaching bridge-imported source.
- **Runtime verification** — drive the real UI in a browser for `W7`; types alone are not evidence
  for a screen.

## 10. Explicitly out of scope

- **Inbound webhooks** (Gubbins receiving a call to mutate inventory). A PWA has no server to receive
  on, and the bridge already has an authenticated write API. Not what #87 asks for.
- **A hosted relay** run by the project to sidestep CORS. That would make Gubbins a service with
  custody of users' inventory events, contradicting its local-first, backend-less design.
- **Delivery with the app closed and no bridge.** Impossible in a browser (§2.4). The UI must say so
  rather than implying otherwise.
- **Fixing the pre-existing `connect-src` gap** for the bridge push / scale URLs (§2.4 box) — real,
  but a separate issue.
