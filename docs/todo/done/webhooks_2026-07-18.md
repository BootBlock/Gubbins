> resolved by closing the item-field gaps first (`W10`), so **`W7` is no longer blocked**: the
> remaining boundary is other *entities* (locations, PO status, suppliers, projects) and hard
> deletion, which `W7` states plainly rather than fixes.
>
> **Carried forward from `W5`:** the §2.4 `connect-src` bug
> ([issue #385](https://github.com/BootBlock/Gubbins/issues/385)) is **not** fixed and is **not**
> a prerequisite for delivery — file-based sync gets subscriptions to the bridge regardless. It does
> mean **push-based** config delivery is affected in production builds, so a user who relies on

Driven by [issue #87](https://github.com/BootBlock/Gubbins/issues/87): *"add full and comprehensive
support for webhooks from directly within the Gubbins PWA itself"* — when something happens in
Gubbins (an item is created, an item moves to a new location, …), call out to a user-configured
URL carrying that event.

Each task has a stable ID (`W0`, `W1`, …) so a session can be kicked off with just "implement `W3`".

## 1. Verdict

**Build it — but the app configures and the bridge delivers.**

The issue's framing ("webhooks from directly within the PWA") implies the browser both *decides* and
*delivers*. The research in §2 shows a browser **cannot reliably deliver** a webhook to the endpoints
users actually own, for four independent reasons — and §6.3 records the decision **not** to weaken the
Content-Security-Policy to partially work around that. Meanwhile the bridge already delivers webhooks
well, and has since EI-1 ([ecosystem-integrations_2026-07-03.md](../ecosystem-integrations_2026-07-03.md) §A1).

| Concern | Where it lives | Why |
| --- | --- | --- |
| **Configuration** — which URL, which events, which filters, what payload | **The PWA** | It is a user-facing feature and belongs in the app's UI, synced like every other user record. This is the whole of what issue #87 is really asking for. |
| **Decision** — "this event matches this subscription" | **Shared pure module in `src/`** | One rule engine, unit-tested once, imported by the bridge across the existing `@/` seam. |
| **Delivery** — the HTTP call, retries, signing | **The bridge, solely** | No CORS, no CSP allowlist, no mixed-content rule, and it keeps running with the tab shut. |

### 1.1 Webhooks require the bridge — and that is a deliberate, cheap line

**The feature does not work without the bridge running.** That sounds like a big concession and is
almost entirely not one: the endpoints direct-from-browser delivery could have reached (Discord,
Zapier, Make, IFTTT — public HTTPS with permissive CORS) are all trivially reachable *from the
bridge*. Direct delivery was only ever about working when **no bridge exists at all**. So the
capability actually lost is: *a user with no bridge who wants a webhook to a CORS-permissive HTTPS
endpoint.*

That is a narrow set, and "run the bridge" is already the answer for MQTT, SSE, Home Assistant, the
iCal feed and the event stream. Webhooks joining that list is consistent, not exceptional.

The UI must therefore state the bridge requirement **up front, before the user builds a
subscription** — not as an error discovered afterwards.

### 1.2 What already exists — and what it actually costs to reuse

> **Corrected after review.** An earlier draft claimed the app could import the bridge's event model
> directly and that the deliverer could be reused unforked. Both were wrong.

- **The event model** — [`bridge/src/events/model.ts`](../../../bridge/src/events/model.ts) maps every
  `HistoryAction` to a stable dotted type (`item.created`, `item.moved`, `stock.adjusted`,
  `item.low_stock`, …). It is pure and well-tested, but **lives on the wrong side of a one-way
  boundary**: [`tsconfig.app.json`](../../../tsconfig.app.json) is `"include": ["src"]`, the root
  `tsconfig.json` is `files: []` + project references, and the `@/*` alias runs **bridge → app only**,
  deliberately (see [`bridge/tsconfig.json`](../../../bridge/tsconfig.json), and
  [`push-to-bridge.ts:15`](../../../src/features/sync/push-to-bridge.ts#L15), which states outright that
  it imports *nothing* from `bridge/`). No file under `src/` imports from `bridge/` today.
  ⇒ **`W0` relocates the event-type map into `src/`** so the app can build its subscription picker
  from it. Scoped deliberately narrowly (§7).
- **The deliverer** — [`bridge/src/events/webhook.ts`](../../../bridge/src/events/webhook.ts): HMAC-SHA256
  signing, `X-Gubbins-Delivery` id, per-target FIFO queue, exponential backoff, failure circuit,
  bounded queue. The retry/circuit machinery is reused as-is — but its `WebhookTarget` is
  `{ url, secret, events? }` with a **required** secret, and its `FetchLike` is
  `{ method, headers, body } → { ok, status }`. It has no concept of per-subscription HTTP method,
  extra headers, payload templates, filters, GET query-flattening, SSRF policy, or outcome capture.
  ⇒ **`W5` is a substantial extension of the target model and request builder**, not a drop-in.
- **The search hook the issue asks for** — *"a hook is called when (e.g.) a search is performed"* is
  **already shipped** as `lookup.resolved`
  ([`bridge/src/events/lookup.ts`](../../../bridge/src/events/lookup.ts), task A2), behind its own
  deliberate opt-in because it publishes what someone searched for. `W7` only surfaces it in the UI.

## 2. Grounding research — why the browser cannot be the deliverer

The evidence for §1, recorded specifically because it is the part most likely to be re-litigated.

### 2.1 CSP pins the outbound origin list at build time

[`src/csp.ts:37`](../../../src/csp.ts#L37) sets:

```
connect-src 'self' https://www.googleapis.com https://world.openfoodfacts.org
```

A user-supplied webhook URL is not on that list, so the fetch is blocked before it leaves the page.
The policy is enforced **twice** — as a service-worker response header ([`src/sw.ts`](../../../src/sw.ts))
*and* as a build-time `<meta http-equiv>` injected from `vite.config.ts` — and a browser enforces the
**intersection** of all delivered policies. That kills the obvious workaround: the service worker
could compute a per-user `connect-src` from stored config, but the static `<meta>` would still veto
it. Supporting arbitrary user URLs from the browser therefore means broadening the *committed* policy
for every user, including those who never configure a webhook. **Declined — see §6.3.**

### 2.2 CORS blocks the request the design needs

A signed webhook is by definition a cross-origin `POST` with a custom header
(`X-Gubbins-Signature`) and `content-type: application/json`. Both make it **preflighted**, so the
receiver must answer an `OPTIONS` with permissive CORS headers. Most webhook receivers do not:
Slack's incoming webhooks and Home Assistant's `webhook` trigger send no CORS headers at all.

The escape hatch, `mode: 'no-cors'`, is worse than it looks — it forbids custom headers (**no
signature**), restricts `content-type` to `text/plain` / form encodings (**no JSON**), and returns an
opaque response (**no way to know if it worked**, so no meaningful retry and no delivery log). A
webhook that cannot be authenticated and cannot be confirmed is not the "full and comprehensive"
support the issue asks for.

### 2.3 Mixed content rules out the primary audience

Gubbins ships to an HTTPS origin. A browser on an HTTPS page cannot fetch `http://` — and the
receivers this feature is for (a Home Assistant instance, a Node-RED flow, a self-hosted automation
box on the LAN) are overwhelmingly plain `http`. Already hit and documented in
[`scale-reading.ts:10-11`](../../../src/features/inventory/scale-reading.ts#L10-L11), where the reading
is fetched *via the bridge* precisely because the PWA cannot reach Home Assistant directly.

### 2.4 Nothing delivers with the tab closed

[`src/sw.ts`](../../../src/sw.ts) registers no one-shot Background Sync listener, and its `periodicsync`
handler explicitly cannot do work itself — it only messages live windows. The database is held under
an exclusive Web Lock by a single tab ([`src/db/tab-lock.ts`](../../../src/db/tab-lock.ts)), so a service
worker cannot read a queued delivery even if one existed. A webhook queued as the user closes the tab
is simply lost.

> **Pre-existing bug found during this research — fix before `W5`.**
> `pushSnapshotToBridge` ([`push-to-bridge.ts:71`](../../../src/features/sync/push-to-bridge.ts#L71)) and
> `scale-reading.ts` both fetch a **user-supplied bridge URL absent from `connect-src`**, both sending
> an `authorization` header (so both are preflighted). In a production build these should already be
> CSP-blocked, and `pushSnapshotToBridge` catches the failure into a message that reads as "the bridge
> is offline", which would mask it.
>
> This was originally scoped out as a curiosity. **The narrowing to bridge-only delivery promotes it:**
> subscriptions now reach the bridge *only* via the synced snapshot, and push is one of the two ways
> that happens (file-based sync is the other, and still works). It should be a separate issue, fixed
> before `W5` lands — note that fixing it means adding the *user's own bridge origin* to `connect-src`,
> which is a different and much narrower question than the one declined in §6.3.

### 2.5 What the browser could have done, and why we are not doing it

Direct delivery would have worked for endpoints that are **HTTPS *and* CORS-permissive** — Discord
webhooks, and many SaaS "catch hook" endpoints. Per §1.1 the bridge reaches all of those anyway, so
the incremental capability was only "works with no bridge at all". That was judged not worth
broadening the CSP for every user (§6.3), so **no direct-from-browser delivery path is planned**.

## 3. Architecture

```
  ┌──────────────────────── the PWA ────────────────────────┐
  │  Webhooks screen ──▶ webhooks table (synced)            │
  │        ▲                      │                          │
  │        │ delivery log (poll,  │ rides the existing       │
  │        │ screen open only)    │ snapshot push / sync     │
  └────────┼──────────────────────┼──────────────────────────┘
           │                      ▼
           │            ┌─── the bridge ──────────────────┐
           │            │ hydrates the DB, derives events │
           └────────────┤ from item_history, matches      │
   GET /api/v1/webhooks/│ subscriptions, delivers         │
   deliveries           └────────────────┬────────────────┘
                                         ▼
                                the user's endpoint
```

**The app never delivers, and therefore never derives events.** Event derivation stays entirely on
the bridge, where it already exists and already works — `createEventPipeline` →
`computeGenerationEvents` → `diffNewEntries` / `buildEvents`, with its own cursor. The app's only
runtime responsibilities are CRUD over subscriptions and reading the delivery log.

> **This is the single biggest simplification in the plan, and it is a consequence of §6.3.** An
> earlier draft had the app deriving events too, which forced: an outbox table, an always-mounted
> polling pump, a persisted cursor with an unavoidable lossy/replay trade-off, a per-subscription
> `route`, device pinning so N synced devices did not fire N times, and an explicit disjointness rule
> to stop the app and bridge double-delivering the same event. **All of that is now unnecessary** —
> there is exactly one deliverer, so duplicate delivery is impossible by construction rather than by
> careful design.

### 3.1 The bridge reads subscriptions from the DB it already hydrates

The bridge **already hydrates the app's database**, so subscriptions in a synced table are readable
with **no new config endpoint, no new token, no new auth surface** — merged with the existing
`webhooks.json` / env targets, which stay supported for operators who prefer file config.

Two honest caveats, both of which must reach the UI and the wiki rather than being buried:

- **Latency.** A new subscription becomes live when the next sync/push reaches the bridge, not
  instantly.
- **One new *read* endpoint is required.** The bridge is strictly read-only over a snapshot that is
  **swapped wholesale on every hydration**
  ([`generation.ts`](../../../bridge/src/events/generation.ts),
  [`pipeline.ts`](../../../bridge/src/events/pipeline.ts)), so it **cannot write delivery outcomes back
  into the DB** — anything it wrote would be discarded on the next hydrate. The bridge therefore keeps
  its own delivery log and exposes `GET /api/v1/webhooks/deliveries` on the existing bearer auth,
  which the app polls **only while the Webhooks screen is open**. Without this, the delivery log and
  "send test event" — the feature's primary debugging affordances — would show nothing at all.

### 3.2 The ledger is the contract

The bridge derives events by diffing the `item_history` ledger, which carries two limits that must be
stated in the UI, not just here:

- **No ledger row → no webhook.** The `W2` audit is in §3.3; it is larger than expected.
- **The window is bounded.** `DEFAULT_EVENT_SCAN_LIMIT = 100` and `DEFAULT_FAN_OUT_CAP = 50`. A bulk
  import writes far more than 100 ledger rows in one go and will emit `events.truncated` rather than
  the user's events. For a feature promising "call my URL when an item is created", this is the more
  surprising limit of the two.

### 3.3 Coverage audit — what can never fire a webhook (`W2`)

**This audit changed what the feature can honestly promise, and is the most important thing `W2`
produced.** It should be read before `W7` writes any UI copy.

#### The structural finding

`item_history.item_id` is declared:

```sql
item_id TEXT NOT NULL REFERENCES items(id) ON DELETE CASCADE
```

([`v1-initial.ts:401`](../../../src/db/migrations/v1-initial.ts#L401)), and `historyStatement` takes
`itemId` as a required first argument. **The ledger is therefore structurally incapable of recording
a non-item event.** Nothing about locations, categories, tags, suppliers, contacts, projects,
purchase orders, bookings, users or roles can ever raise a webhook as things stand — not because a
call site was forgotten, but because there is no row shape to write. Closing that needs either a
nullable `item_id` plus an entity-type column, or a second event source. Both are real projects, and
**neither is in scope for #87.**

#### Entities with no event coverage at all

Tags · categories & custom-field values · contacts · suppliers · supplier parts · asset bookings ·
attachments · images · users · roles · projects (lifecycle, budgets, BOM lines) · wishlist ·
tare presets · webhook subscriptions themselves. Every create / rename / update / delete of these is
silent.

Several of these are **item-scoped yet still silent**, which is where users will be most surprised:
tagging an item (`TagRepository.setForItem`), setting its custom-field values
(`CategoryRepository.setItemFieldValues`), adding an image or attachment, and adding a supplier part
are all changes *to an item* that write no ledger row.

#### Partially covered entities

- **Locations** — only `RE_PARENTED` is emitted, and only *per orphaned item* when a location that
  contains items is deleted. Creating, renaming, archiving or setting a default location fires
  nothing; deleting an *empty* location fires nothing at all.
- **Purchase orders** — goods receipt (`RECEIVED`) and supplier return are covered. `setStatus` is
  **not**, so "PO ordered" / "PO cancelled" — the most obviously useful PO webhook — cannot fire.
  Nor can creating, editing, deleting a PO or any line change.
- **Maintenance** — completion is logged; *scheduling* is not, and "a schedule became due" is a
  derived query rather than a ledger row, so it can never be an event.
- **Projects** — only ever logged against the *item* (reserved, procured, consumed, assembled). No
  project lifecycle event exists.

#### Item-level gaps — **mostly closed by `W10`**

As audited, `ItemRepository.update` logged **three** of roughly thirty mutable fields — `name`,
`trackingMode` and `condition` — and everything else fell through to a bare `UPDATE` with no ledger
row. Since no ledger row means no webhook, changing an item's price notified nobody.

**`W10` closed the fields users expect a notification for.** Each now writes a single
`ATTRIBUTES_CHANGED` entry mapped to the already-published `item.changed` type:

| Group | Fields |
| --- | --- |
| Price | `unitCost`, `purchasePrice`, `currentValue` |
| Identity | `barcode`, `serialNumber` |
| Classification | `categoryId` |
| Reordering | `reorderPoint`, `reorderGaugePercent`, `reorderQty` |
| Perishables | `expiryDate` |

One entry covers the whole edit rather than one per field, and **a field set to the value it already
holds is not a change** — re-saving an unedited form writes nothing and fires nothing. Which fields
moved rides the entry's `note` ("Changed unit cost, barcode.") and its `metadata`
(`{ fields: ['unitCost', 'barcode'] }`). The note reaches webhook consumers as the payload's
`detail`; `metadata` is **not** currently carried on `BridgeEventData`, so a consumer that needs the
machine-readable field list would need that payload addition — deliberately not made here, as it
changes a published contract.

`W10` deliberately did **not** add a value delta to these entries. `net_value_delta` carries realised
movement for the sales/margin report (`SOLD`); populating it for a revaluation would distort that
report and render a spurious delta badge in the Activity Log.

**Still silent after `W10`** (a deliberate boundary, not an oversight): notes/description,
manufacturer/MPN, batch & lot, warranty and depreciation, dimensions and weight — none of which a
user would expect a notification for. Also still silent, and **left alone by design** because they are
reporting preferences rather than changes to what the item is: `isFavourite`, `isUnlimited`,
`deadStockMode`.

Also still silent: item relations, aliases, capabilities, kit composition edits (as distinct from
assemble/disassemble), and deleting a test record.

> **Knock-on for `W7`:** bulk **import updates** go through `update`, so an import that revises
> prices now emits a burst of events where it previously emitted none. That is correct, but combined
> with `DEFAULT_FAN_OUT_CAP = 50` it can now trip `events.truncated` in cases that previously stayed
> under the cap. The UI should keep saying that a bulk change is better consumed via the REST API
> than the event stream.

#### Deletion is the sharpest gap

`ItemRepository.hardDelete` ([`item/core.ts:525`](../../../src/db/repositories/item/core.ts#L525)) runs
`DELETE FROM items` plus a tombstone, and nothing else. Because `item_history.item_id` cascades,
**the item's entire ledger is destroyed in the same transaction**. So a permanent deletion does not
merely fail to emit an event — it retroactively removes history the differ may not yet have read.

> **The cheap fix, recorded for a future phase:** `tombstoneStatement` *is* written on hard delete
> (items, locations, relations, aliases), into a `tombstones` table the event pipeline currently
> ignores. That table is a ready-made deletion feed, and it covers locations too. Deriving
> `*.deleted` events from tombstones is very likely the least-effort way to close the deletion gap —
> but it is a **new event source**, not a tweak, so it belongs in its own phase rather than being
> smuggled into `W5`.

Two further caveats worth carrying into `W5`:

- **`StorageRepository.pruneHistoryBefore` deletes ledger rows** and advances a watermark the
  reconcile engine then refuses to re-import. Pruning can move rows out from under a cursor.
- **Bulk import creates are covered** (`createMany` → `buildInsert` always appends a `CREATED` row),
  so an N-row import emits N events in one transaction — which is precisely what trips the
  `events.truncated` cap above. Import *updates*, however, go through `update` and therefore inherit
  every gap in the item-level list.

#### What this means for the UI (`W7`)

The subscription picker must not imply coverage the engine cannot deliver. Concretely: describe
events in terms of **what the ledger records**, do not offer categories of event that cannot fire,
and state plainly that webhooks presently cover **changes to items** — not locations, purchase-order
status, or anything else in the list above. A user who configures "notify me when anything changes"
and silently misses one is worse served than one who was told the boundary up front.

**After `W10` the boundary is entity-shaped rather than field-shaped**, which is a much easier thing
to say honestly: the item edits a user would expect to be notified about *do* fire (price, barcode,
serial number, category, reorder thresholds, expiry, plus the pre-existing name / tracking mode /
condition and every stock movement). What remains outside is **other entities** — locations, PO
status, suppliers, projects, tags, custom-field values — and **hard deletion**, both of which need a
wider ledger or a second event source and are their own issues. `W7` states these as boundaries; it
does not fix them.

## 4. Data model

**One** new table, folded into the **squashed v1 baseline** per the pre-release policy in
[`src/db/migrations/index.ts`](../../../src/db/migrations/index.ts) — *not* a v2 migration.

> An earlier draft also specified a local `webhook_queue` outbox/log table. **It is no longer needed**:
> the app never delivers, so there is nothing to queue, and the delivery log lives on the bridge and
> is read over the §3.1 endpoint.

### 4.1 `webhooks` — the subscriptions (synced)

Shaped like the `wishlist` / `tare_presets` precedent: an independent LWW leaf, no FKs, `STRICT`,
UUID TEXT PK, UNIX-ms timestamps, and the standard `updatedAtTrigger` helper (never an inlined
trigger — the `MAX(now, OLD.updated_at + 1)` and `WHEN NEW.updated_at = OLD.updated_at` invariants are
load-bearing for sync).

| Column | Notes |
| --- | --- |
| `id` | UUID |
| `name` | user label, e.g. "Discord #inventory" |
| `url` | `http(s)` absolute |
| `method` | `POST` \| `GET` \| `PUT` \| `PATCH` — the issue explicitly asks for more than POST |
| `enabled` | integer bool |
| `secret` | HMAC signing secret; nullable (§6.1) |
| `secret_ref` | name of a bridge-side secret, the recommended option (§6.1); nullable |
| `event_types` | JSON array of dotted types, or `["*"]` |
| `filter` | JSON filter expression (§5.2), nullable |
| `template` | payload template (§5.3), nullable = default envelope |
| `headers` | JSON object of extra static headers, nullable |
| `created_at` / `updated_at` | standard |

Exactly one of `secret` / `secret_ref` is set (app-enforced). No `route` and no `direct_device_id` —
there is only one deliverer.

## 5. Feature design

### 5.1 Event catalogue

The subscribable list is a **hand-maintained catalogue assembled from four sources**, with a drift
test asserting it stays a superset of what the engine emits:

> **Corrected after review.** An earlier draft claimed the catalogue could be *generated* from
> `ACTION_EVENT_TYPE` such that it "cannot drift". It cannot: `eventTypeForAction` falls back to
> `'item.changed'` for unknown actions (an **open set**, so the reverse direction isn't derivable),
> `events.truncated` is emitted and absent from the map, `item.low_stock` / `item.out_of_stock` are
> derived in `statusEvent`, and `lookup.resolved` lives in `lookup.ts`.

Presented in the UI as a grouped, human-labelled picker, never a raw string field. Includes
`lookup.resolved`, which the UI must mark clearly as *"publishes what was searched for"* and leave off
by default, mirroring the bridge's deliberate separate opt-in.

### 5.2 Filters

Beyond event type, a subscription can narrow by a small, **declarative, JSON-serialisable** filter —
location subtree, category, tag, item, or a quantity threshold. It must be a data structure evaluated
by a pure matcher, **never** a user-supplied expression string that gets `eval`'d or interpreted.
Follow the existing search AST discipline (`parseTextQuery` → AST → evaluate; memory note
`phase-47-scope-decisions`) rather than inventing a second query language.

> **Shipped in `W3`** — [`src/features/webhooks/filter.ts`](../../../src/features/webhooks/filter.ts).
> The vocabulary is a discriminated union on `kind`: the combinators `all` / `any` / `not`, the
> inert `none`, and the leaves `location` (subtree by default) / `category` / `tag` / `item` /
> `quantity`. `WebhookFilter` is no longer opaque — `types/webhooks.ts` re-exports this type, and
> both the repository and the plan seam parse on the way in, so only the canonical shape is ever
> stored. Two rules decide the safe direction, and `W5` must not soften either:
>
> - **An unconfirmable fact does not match.** An event carrying no item (`lookup.resolved`,
>   `events.truncated`) fails every item-scoped test rather than being waved through.
> - **A filter that cannot be parsed becomes `none`, never `null`.** These rows arrive over sync
>   from peers on other builds, and softening an unrecognised filter to "no filter" would silently
>   *widen* the subscription to every event of its types. This has to hold **under negation** as
>   well: a `not` whose child failed to parse propagates the failure rather than inverting the
>   inert node into "match everything".

### 5.3 Payload templates

Default is the existing `BridgeEvent` envelope — unchanged, so anything already consuming bridge
webhooks keeps working. Optionally the user picks a **preset** (Discord, Slack, Home Assistant,
generic) or supplies a template with `{{event.type}}`-style placeholders resolved by a pure,
**allow-listed** interpolator: an explicit list of permitted paths, no arbitrary property traversal
and no code, so a template can never surface something the event did not already contain.

For `GET`, the payload flattens into query parameters instead of a body (the issue explicitly asks
for `GET`); the UI must note that a `GET` cannot carry an HMAC body signature.

> **Shipped in `W3`** — [`src/features/webhooks/template.ts`](../../../src/features/webhooks/template.ts),
> over the closed [`event-view.ts`](../../../src/features/webhooks/event-view.ts) projection.
>
> - **The view *is* the allow-list.** `src/` cannot import `bridge/`, so rather than reading a
>   `BridgeEvent` structurally the deliverer projects whatever event it holds into a flat, closed
>   `WebhookEventView`. There is then no traversal to restrict, because nothing else is in scope —
>   a template cannot reach the subscription's secret, its headers, or another item.
> - **Presets are encoded in the existing column** as `preset:<name>`, so `W1`'s schema stands.
>   An unrecognised preset (a newer peer's) falls back to the **default envelope**, not to an empty
>   body.
> - **The default payload is not rebuilt here.** `resolveWebhookPayload` returns an `envelope`
>   marker and `W5` serialises the event it already holds — re-deriving the envelope would fork the
>   payload contract into a second place.
> - **`GET` flattening** drops nulls (a query string cannot express one) and sends a free-text
>   template as a single `payload` parameter.

### 5.4 Making the bridge dependency legible

Per §1.1 the feature does not work without the bridge. The UI must carry that plainly:

- the Webhooks screen states the requirement **before** the user builds a subscription, with a link to
  the bridge setup guide, and offers to create one anyway (it will start delivering once the bridge is
  up) rather than blocking;
- a live bridge-reachability indicator, reusing whatever the Sync screen already does rather than
  inventing a second health check;
- the hydration latency from §3.1 shown as "changes reach the bridge on the next sync", not hidden.

This is the single most likely source of "it doesn't work" confusion, and the design should absorb
that cost up front.

### 5.5 Test-fire

Every subscription gets **"Send test event"**, producing a synthetic event through the real matcher,
template and delivery path, writing a real bridge-side log row. The result arrives via the
`GET /api/v1/webhooks/deliveries` poll (§3.1) — which is why that endpoint is not optional.

## 6. Security

### 6.1 The signing secret — simplified by the §6.3 decision

> **Corrected after review, then simplified.** An earlier draft proposed "store it in the row, let it
> sync, but redact it from backups via `SYNC_EXCLUDED_COLUMNS`". That is **self-defeating**:
> `SYNC_EXCLUDED_COLUMNS` ([`tombstone.ts:179`](../../../src/db/repositories/tombstone.ts#L179)) is applied
> inside the *shared* snapshot builder used by sync, backup **and** the bridge push, so excluding
> `secret` there strips it from the very payload the bridge hydrates — **bridge signing dies**. A
> backup-only redaction would be `filterSnapshot` in
> [`backup-format.ts`](../../../src/features/backup/backup-format.ts) instead, but even that is defeated
> by `rawSqlite` (a byte copy of the whole DB) in `build-backup.ts`. And it worried about the backup
> while ignoring the leakier artefact: the **sync** file, which by design sits on a NAS or in the
> user's Google Drive.

**Dropping direct delivery removes the constraint that forced the bad answer.** The browser no longer
needs the secret at all — only the bridge signs. So:

1. **`secret_ref` — bridge-side secret (recommended, and the default the UI steers to).** The row
   stores only a *name*; the value lives in the bridge's git-ignored `webhooks.json` / env and
   **never enters the database, the sync artefact, or any backup**. Strictly better, and now costs the
   user only one config line, since they are already running a bridge (§1.1).
2. **`secret` in the row (convenience fallback).** Zero setup, but the value travels in the sync
   artefact in plaintext. Generate it (never user-invented), show it **once** with a copy button,
   offer regenerate-only afterwards, and **say plainly in the UI and the wiki** that it travels with
   synced data.

`W1` should confirm this ordering, but the security argument for defaulting to (1) is now
straightforward in a way it was not before.

### 6.2 SSRF and the local network

A user-configured URL is a request-forgery surface, and now **entirely** on the bridge, which sits on
the LAN and can reach things the browser cannot. The bridge must refuse to deliver to
loopback/link-local/metadata addresses unless the operator explicitly opts in via an env flag, in
keeping with the bridge's existing off-by-default posture for anything with reach. With the browser
path gone, this is the feature's primary security control and should be treated as such — not a
footnote in `W5`.

### 6.3 CSP — decision: **declined, do not broaden**

Direct browser delivery would have required broadening `connect-src` (§2.1). **This was considered and
rejected:** it widens the outbound surface for every user — including everyone who never configures a
webhook — to buy a capability the bridge already provides for all but a narrow case (§1.1, §2.5).

`src/csp.ts` is **not modified by this plan.** A future proposal to revisit this should be argued on
its own merits rather than inherited from here.

Note the separate, much narrower question raised by the §2.4 box: allowing the *user's own bridge
origin* so the existing push/scale calls work. That is a real bug fix, is scoped to one
user-configured origin rather than the open web, and is **not** what was declined here.

### 6.4 Everything else

No secret, signature, or token in any log, error message, or delivery record. `redactUrl` for
diagnostics. User-supplied extra headers are validated against a deny-list so a template cannot forge
`authorization` onto an unrelated host without the user's intent being explicit.

### `W7` — what shipped, and what `W8` must document

**Three deviations from the `W7` row above**, each deliberate:

1. **`presets.ts` was not touched.** The touch-point checklist (§8) lists it, but the curated
   presets deliberately carry **no integrations** — neither `sync` nor `home-assistant` appears in
   any of them — and `OPTIONAL_FEATURE_IDS` is *derived* from the registry, so the `everything`
   preset picks `webhooks` up automatically. Adding webhooks to a preset while its two sibling
   integrations stayed out would have been the inconsistent choice.
2. **Test-fire (§5.5) required new bridge work.** `W5` shipped the delivery-log *read* endpoint but
   no way to *send* a test, so `W7` added **`POST /api/v1/webhooks/test`**. It fires a synthetic
   event through the real matcher, template, SSRF guard and deliverer, and writes a real log row.
   The row→target mapping was extracted out of `loadDatabaseWebhookTargets`' loop so the endpoint
   and the normal path share one definition of `secret_ref` resolution and header sanitisation.
   A latent defect was fixed alongside it: `createBridgeServer` did not thread `webhookDeliveries`
   on the **POST** path (only on GET), which would have made the endpoint permanently invisible.
3. **The filter builder edits a subset of the tree.** It offers one combinator (`all`/`any`) over a
   flat list of `location` / `category` / `tag` / `quantity` leaves. Anything else — a nested tree,
   a `not`, the inert `none`, or an `item` leaf — is detected by the pure `webhookFilterToForm`,
   shown **read-only**, and left untouched unless the user explicitly replaces it. These rows arrive
   over sync from peers on other builds, and silently rewriting a filter the editor only partly
   understood would change what a subscription delivers without anyone asking. **An `item` leaf is
   therefore not creatable in the UI** — worth its own follow-up if it turns out to be wanted.

**Both gaps `W7` left open are now closed** (follow-up change):

- **Extra headers are editable.** The dialog has a name/value editor, and the header rule from §6.4
  moved into [`src/features/webhooks/headers.ts`](../../../src/features/webhooks/headers.ts) so the
  **app checks the very list the bridge enforces** — the bridge imports it back over the existing
  one-way `@/` alias, exactly as `W0` did for the event-type map. A refused name is now reported as
  it is typed, and says *which* rule it breaks (`authorization` carries credentials; `X-Gubbins-*`
  is computed by the deliverer and would let a subscription forge its own signature). Saving is
  blocked while any row is refused, so `INVALID_HEADERS` is reachable and meaningful. A UI copy of
  a security list that drifted from the enforced one would have been worse than no check at all.
- **The `item` filter leaf is editable**, sourced from a search rather than a full dropdown — an
  inventory can hold far more items than belong in a list. Already-chosen items are resolved by id
  so a selection still reads as names once the search box is cleared. `webhookFilterToForm` now
  represents `item`; the read-only fallback remains for nested trees, `not` and the inert `none`.

**A real bug the follow-up's browser pass found, and fixed:** the payload-format editor derived its
mode from the stored template on every render. A freshly-chosen **Custom** starts as an *empty*
template, which is indistinguishable from "no template", so the mode snapped straight back to the
envelope — **the custom-template editor could never be opened at all**. The editor now *holds* its
mode (the stored value remains the single source of truth for what is *sent*), with the seeding
mapping extracted to a pure, tested `template-mode.ts`. Types, unit tests and review had all passed
over this; only driving the real screen surfaced it.

**Notes for `W8` (the wiki page):**

- **Lead with the bridge requirement.** The screen states it before the list and still allows
  creating a subscription; the page should read the same way round.
- **The secret trade-off, in the §6.1 order.** `secret_ref` is the default the UI steers to and the
  value never enters the database, sync artefact or backup. The in-row `secret` is generated (never
  user-typed), shown **once** with a copy button, and only regenerable afterwards. An unresolvable
  `secret_ref` **drops the subscription rather than delivering it unsigned**, and shows as a
  `blocked` row.
- **`GET` carries no signature** — said in the app where the method is chosen, and worth repeating.
- **The LAN opt-in is configuration, not an error.** `GUBBINS_BRIDGE_WEBHOOKS_ALLOW_PRIVATE=on` is
  what a Home Assistant / Node-RED receiver needs, and that is the *expected* setup.
- **Hydration latency.** Subscriptions reach the bridge on the next sync, not instantly.
- **Coverage, honestly (§3.3).** Item changes fire; **locations, purchase-order status, suppliers,
  projects, tags, custom-field values and hard deletion do not.** The screen says this in
  `webhooks.notes.coverage` — the wiki should not promise more than that string does.
- **The delivery log only updates while the screen is open**, and its `not-enabled` (404) state
  means webhooks are off on the bridge — deliberately distinct from "nothing delivered yet".
- **Screenshots** need a capture step adding to `scripts/wiki-screenshots.mjs`, with synthetic data
  only.

**Known live constraint, unchanged by `W7`:** the delivery-log poll and test-fire are both app→bridge
calls to a user-configured origin, so [issue #385](https://github.com/BootBlock/Gubbins/issues/385)
(`connect-src`) affects them in production builds exactly as it affects push and the scale reads.
Subscriptions still reach the bridge over file-based sync regardless, so delivery itself is
unaffected — but the log may read as "bridge unreachable" until #385 is fixed. Out of scope here.

`W4` and `W6` are **retired** — they were the app-side delivery pump and the direct-from-browser path,
both removed by the §6.3 decision. The ids are left unused rather than renumbered so this document and
the issue history stay legible. `W10` was inserted after `W5` for the same reason: it is numbered
past the retired ids rather than reusing one.

**Recommended order:** `W0 → W1 → W2 → W3 → W5 → W10 → W7 → W8 → W9`. `W0` and `W1` are independent and can
run in parallel. The §2.4 CSP bug should be fixed as its own issue before `W5`.

## 8. Touch-point checklist

Every one of these is required, and several **fail the build** if missed rather than merely being
forgotten.

**DB** — `migrations/v1-initial.ts` (`CREATE TABLE` + `updatedAtTrigger` + indexes) ·
`__fixtures__/schema-baseline.snapshot.json` (**deliberate regeneration** — `v1-initial.test.ts`
asserts byte-for-byte, so this fails by design until updated) · `repositories/WebhookRepository.ts` ·
`repositories/index.ts` (export **and** `getWebhookRepository()` accessor — two separate blocks) ·
`repositories/types.ts` + mapper · `tombstone.ts` `SYNC_TABLES`.

**Modules** — `feature-registry.ts` (`FeatureId` **and** `FEATURE_DEFS`; typed `Record`, so one
without the other is a compile error) · `nav-destinations.ts` (`AppRoutePath` **and**
`NAV_DESTINATIONS`; a registry-integrity test asserts the route↔feature pairing both ways) ·
`presets.ts` · `en.json` **and** `de.json` (the `messageKey` value must be **byte-identical** to the
`NavDestination.label` — a drift test pins it).

**Routes** — `src/routes/webhooks.tsx` wrapped in `ModuleGuard` · regenerate `routeTree.gen.ts`
(generated by the Vite plugin, not `tsc` — run `npx vite build` once before type-check) · a pure `.ts`
and a component `.tsx` must not share a basename.

**Bridge** — target sourcing from the hydrated DB · `secret_ref` resolution · SSRF guard · the new read
endpoint · **no TS parameter properties / `enum` / `namespace` anywhere the bridge imports** (Node's
strip-only loader; `npm run smoke:bridge` is the only check that catches it — `tsc` and Vitest both
bypass it) · `bridge/README.md`.

**Not touched** — `src/csp.ts` (§6.3).

**Docs** — `docs/wiki/` page + sidebar + page map in `wiki_2026-07-11.md` · this doc's status banner
kept current, and moved to `done/` when the last phase lands.

## 9. Testing

- **Pure modules** (`W2`, `W3`) — exhaustive unit tests; this is where the real logic lives and it is
  all I/O-free by construction.
- **`W0`** — the existing bridge event tests must pass unchanged; that is the refactor's proof.
- **Repository** (`W1`) — against the `node:sqlite` in-memory driver, as every other repository does.
- **Delivery** (`W5`) — the existing `webhook.test.ts` injects `fetchImpl`, `sleep` and `now`; follow
  it exactly. No real network in tests.
- **SSRF guard** (`W5`) — explicit tests that loopback, link-local and metadata addresses are refused
  unless the opt-in flag is set. This is the feature's primary security control (§6.2).
- **Secret containment** (`W1`) — an explicit test that a `secret_ref` subscription puts **no secret
  value** in the database, and therefore none in a snapshot or backup.
- **`npm run smoke:bridge`** — mandatory for `W0` and any change reaching bridge-imported source.
- **Runtime verification** — drive the real UI in a browser for `W7`; types alone are not evidence
  for a screen.

## 10. Explicitly out of scope

- **Direct-from-browser delivery** and any `connect-src` broadening to support it (§6.3).
- **Inbound webhooks** (Gubbins receiving a call to mutate inventory). A PWA has no server to receive
  on, and the bridge already has an authenticated write API. Not what #87 asks for.
- **A hosted relay** run by the project to sidestep CORS. That would make Gubbins a service with
  custody of users' inventory events, contradicting its local-first, backend-less design.
- **Delivery with no bridge.** Impossible in a browser (§2), and now an explicit product line (§1.1).
- **Fixing the `connect-src` gap** for the existing bridge push / scale URLs (§2.4 box) — real, and
  now promoted to "fix before `W5`", but its own issue.
